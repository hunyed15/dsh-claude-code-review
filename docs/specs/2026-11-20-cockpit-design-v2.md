# 项目驾驶舱 · 设计 v2（集成层）

> 2026-11-20 · 取代 v1 的"审核插件附带看板"叙事
> v1：[2026-11-18-project-cockpit-design.md](2026-11-18-project-cockpit-design.md)（历史，仍可读）

## 1. 定位：它到底在做什么

一句话：**把已有工具产出的状态，收拢成一处可读、可行动的现场。**

它不生产业务数据。它做的是：

| 它做的 | 不是它做的 |
|---|---|
| 读别人写的数据，归一成四类事实 | 不解析 PRD 文本、不猜 worktree |
| 把事实投射成一屏可读的现场 | 不重造待办、不做甘特图/趋势图 |
| 给出唯一动作，并把它交给会话执行 | 不替人做决策，不自动合并代码 |

**判断某个功能该不该进这个插件，只有一条标准**：
它是否在回答「项目在哪 / 卡在哪 / 谁在干 / 下一步」之一，且数据来自已有源。
否则不做。

## 2. 四层架构（硬约束）

```
适配器层   每个源一个适配器：{ id, read(), 版本假设, 降级文案 }
           trellis · 审核账本 · sessions · (将来)任务板/验收结果/外部插件
   ↓ 只读、可选、互不依赖；一个源坏了只影响它自己
归一化层   四类事实：feature / defect / gate / session（纯函数、可单测）
   ↓
视图层     生命周期 + 三本账 + 并行（只认归一化事实，不认任何插件私有格式）
   ↓
行动层     唯一动作 + 两步发送（面板落槽位 → 对话通栏发送）
```

**硬约束**：视图层永远不知道数据来自哪个插件。新增数据源 = 新增一个适配器，不动视图层。

## 3. 四类事实与数据源

| 事实 | 数据源 | 可靠性 | 读不到时 |
|---|---|---|---|
| **feature**（功能） | `.trellis/tasks/*/task.json`：`title / status / subtasks / relatedFiles` | 精确字段 | 任务表为空，页面显示"未初始化" |
| **defect**（缺陷） | 审核账本 `review-N.json` 的 `review.issues` + `dispositions.jsonl` | 精确字段（`failOn` 取 `meta.failOn`） | 该功能缺陷列显示 `—`，不显示绿色 0 |
| **gate**（阶段门） | 上面两者 + `.trellis/spec/**` 数量 | **推断**，每道门带 `basis` | 整屏降级为「待确认」 |
| **session**（并行） | `sessionQuery.listSessions()` + `ctx.sessions.list()` + `SessionHeader` | 精确字段 | 并行区显示原因，其余不受影响 |

### 3.1 功能 = trellis 任务（不再单独建功能表）

历史上试过"解析 PRD 勾选算完成度"，结论是**算不出来**（自由格式 markdown，没有条目契约），已作废。

v2 的替代方案不新增任何数据源：

- **功能** = 一个 trellis task
- **功能的作用域** = `task.relatedFiles`（已有字段，用户已在用）
- **缺陷归属** = 审核报告的 `issue.file` 按路径前缀匹配 `relatedFiles`

于是"哪个功能还有几个 bug"变成一次精确匹配，而不是一句话。

匹配不上任何功能的缺陷归入 **「未归属」** 单列，如实显示——不硬塞、不丢。

## 4. 视图：一屏回答五个问题

| 区 | 回答 | 说明 |
|---|---|---|
| 下一步 | 现在该做什么 | 状态机唯一输出 + 指令原文 + 理由；保留两步发送 |
| 生命周期 | 走到第几阶段 | 7 道门压成一条进度线，当前门一句话 + 依据（推断，必须标） |
| **三本账** | 功能 / 缺陷 / 门禁 | 功能清单按 task 列：状态、作用域、待修数、最近轮次；未归属缺陷单列 |
| 并行 | 谁在干、会不会撞 | 会话树 + 目录 + 活否 + 撞车预警（P1 已实现） |
| 数据可信度 | 这些数字能不能当真 | 顶部 chip 三态（正常 / 待确认 / 有待修），异常横幅列原因 |

原则：**同一屏内口径必须一致**。数据不可信时，chip、下一步、门禁、表格一起降级（v2.1.x 已建立）。

## 5. 行动层

- 一步只有一个主按钮：`去对话发送` → 通栏确认 → 走用户自己的发送通道。
- 面板是 root scope，拿不到 `inputActions`，所以必须两步；这条是硬约束不是懒。
- 将来允许的额外动作（N3）：`催一下`（向指定会话 steer）、`开始集成`（发给 integrator）。同样是两步发送，不新增特权通道。

## 6. 非目标（写死，防止膨胀）

- 不重造 dsh-todos 的待办、不做甘特图/趋势图/热力图
- 不写项目里任何文件；要存也只存 `.dsh/plugin-state/`（trellis 不托管）
- 不解析 PRD 文本、不跑 git 判定 worktree、不给"看起来像"的数字
- 不做多项目同时看板（单项目多 agent，跨项目预留字段但不实现）

## 7. 命名与分发（本次变更）

这个包已经不是"审核插件"：审核只是它的一个数据源。

| 项 | 变更 |
|---|---|
| 包名 | `@hunyed15/claude-code-review` → **`@hunyed15/project-cockpit`** |
| GitHub 仓库 | `dsh-claude-code-review` → **`dsh-project-cockpit`**（GitHub 自动重定向旧 URL） |
| 旧独立仓库 | `hunyed15/project-cockpit` 保持归档状态（与 `dsh-project-cockpit` 不冲突） |
| 本地目录 | 暂不改名（profile 链接指向它；迁移需 remove_bundle → 移动 → install_bundle） |
| 插件行 id | 保持 `claude-code-review`（改名会让 profile 里的旧行悬空，风险大于收益） |
| 版本 | **3.0.0**（包名变更 = 破坏性） |

安装命令（新）：

```powershell
plugin_manager(action: "install_bundle", target: "git+https://github.com/hunyed15/dsh-project-cockpit.git")
```

## 8. 迁移步骤（必须按序，否则会出重复别名）

上一轮踩过：profile 里同时存在 `@local/...` 与 `@hunyed15/...` 两个包名指向同一目录，行 id 重复导致插件激活失败。

1. `remove_bundle("@hunyed15/claude-code-review")`（如有旧 alias 一并移除）
2. 改 `package.json` 名字与 `cordis.patch.yml` 行名、`client.js` 模块 id
3. `install_bundle(<本地目录>)`
4. 确认 `plugin_manager` 返回 `application: applied`（不是 `failed`）
5. `listTools` 里能看到四个工具；两条路由 200
6. 重启 DSH 后再验一遍

## 9. 里程碑与验收

| 步 | 内容 | 验收标准 |
|---|---|---|
| **N1** | 功能清单 + 缺陷按 `relatedFiles` 归属 + 未归属单列 | 真实仓库上"每功能待修数"与手工核对账本一致；未归属数量正确 |
| **N2** | 任务板接入：认领 + 写作用域 + 跨目录冲突 | 派活后并行区显示"谁在做什么"；两个任务 scope 交集 → 预警 |
| **N3** | 行动：催一下 / 开始集成 + 集成后自动 gate | 点击后目标会话真的收到消息；集成后自动出一条审核轮次 |
| **N4** | 外部源（dsh-todos / 验收结果） | **按需**，每加一个源必须有降级与单测 |

## 10. 风险

| 风险 | 对策 |
|---|---|
| 每接一个源就多一份格式依赖 | 适配器层隔离 + 每个源必须有"读不到"的分支与文案 |
| 功能归属靠路径前缀匹配，可能误挂 | 未归属单列；界面标注"按路径推断"；不做模糊匹配 |
| 改名导致用户安装失败 | GitHub 仓库重定向 + README 两处地址同步 + 迁移步骤写死 |
| 面板信息过载 | 每区最多 N 行 + 截断提示；不做图表 |
| 之前发生过的"数字造假" | 禁止用"看起来合理"的默认值（blocking=0 那次教训已写成断言） |
